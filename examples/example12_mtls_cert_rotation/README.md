# Example 12: Advanced mTLS with Certificate Rotation

This example demonstrates a gRPC client and server setup that simulates mTLS (mutual TLS) with server-side certificate rotation and client-side dynamic CA trust updates.

## Concepts Demonstrated

1.  **Initial mTLS Setup**: Client and server start with an initial set of certificates (CA v1, Server v1, Client v1). All communication is encrypted and mutually authenticated.
2.  **Certificate Generation**: The `certs.py` script handles the generation of multiple versions of CA, server, and client certificates using `pyvider-rpcplugin`'s crypto utilities.
    *   `ca_v1.pem`, `server_v1.pem`, `client_v1.pem` (Server v1 is initially signed by CA v1 and set to expire in 1 day for demo purposes).
    *   `ca_v2.pem`, `server_v2.pem`, `client_v2.pem` (Server v2 is signed by CA v2).
    *   `server_v3.pem` (Server v3 is signed by the original CA v1).
3.  **Server-Side Certificate Rotation (RPC Triggered)**:
    *   The server exposes a `RotateCert` RPC.
    *   When called, the server simulates rotating its certificate. The example cycles through:
        1.  Initial: `server_v1.pem` (signed by `ca_v1.pem`). Client trusts `ca_v1.pem`.
        2.  Rotation 1: Server switches to `server_v3.pem` (signed by `ca_v1.pem`). The CA trusted by the client (`ca_v1.pem`) remains the same. The server updates its credentials.
        3.  Rotation 2: Server switches to `server_v2.pem` (signed by `ca_v2.pem`). The server also changes its policy to only trust clients signed by `ca_v2.pem`. The client needs to update its CA trust to `ca_v2.pem`.
        4.  Rotation 3: Server switches back to `server_v1.pem` (signed by `ca_v1.pem`), and trusts clients signed by `ca_v1.pem` again.
    *   The server stops and restarts its gRPC service endpoint to apply the new certificates. This will drop existing connections, simulating a scenario common in simpler rotation setups. Zero-downtime rotation is significantly more complex.
4.  **Client-Side CA Trust Update**:
    *   The server exposes a `GetNewCACert` RPC.
    *   If the client detects (based on `RotateCert` response) that the server's CA might have changed, it calls `GetNewCACert`.
    *   The client saves the new CA certificate and updates its gRPC channel to trust this new CA for future connections to the server.
5.  **Simulated Certificate Expiry**: `server_v1.pem` is generated with a short validity (1 day) to facilitate testing scenarios where a certificate might expire. The server includes a background task to log the status of this certificate.

## Files

*   `service.proto`: Defines the gRPC service (`Greeter`) with `SayHello`, `RotateCert`, and `GetNewCACert` RPCs.
*   `certs.py`: Script to generate and manage all necessary X.509 certificates and private keys. Creates a `.certs/` directory.
*   `server.py`: Implements the gRPC server, including the logic for certificate rotation and serving the new CA.
*   `client.py`: Implements the gRPC client, which calls RPCs, triggers server certificate rotation, and updates its CA trust.
*   `README.md`: This file.
*   `__init__.py`: Makes the directory a Python package.
*   `service_pb2.py`, `service_pb2_grpc.py`: Generated Python code from `service.proto`. (Generated by running the protoc command).

## Prerequisites

*   Python 3.8+
*   `grpcio`, `grpcio-tools`
*   `pyvider-rpcplugin` (which includes cryptography)

Install dependencies (preferably in a virtual environment):
```bash
pip install grpcio grpcio-tools pyvider-rpcplugin
```

## Running the Example

1.  **Generate Protocol Buffers Code**:
    Navigate to the `examples/example12_mtls_cert_rotation` directory and run:
    ```bash
    python -m grpc_tools.protoc -I. --python_out=. --grpc_python_out=. service.proto
    ```
    This will generate `service_pb2.py` and `service_pb2_grpc.py`.

2.  **Generate Certificates**:
    The `certs.py` script will be run automatically by `server.py` if the `.certs` directory is missing. However, you can run it manually to see the output:
    ```bash
    python certs.py
    ```
    This will create a `.certs/` subdirectory with `ca_v1.pem/key`, `server_v1.pem/key`, `client_v1.pem/key`, `ca_v2.pem/key`, `server_v2.pem/key`, `client_v2.pem/key`, `server_v3.pem/key`.

3.  **Start the Server**:
    In a terminal, run:
    ```bash
    python server.py
    ```
    The server will start, initially using `server_v1.pem` and `ca_v1.pem`.

4.  **Run the Client**:
    In another terminal, run:
    ```bash
    python client.py
    ```
    The client will:
    *   Connect using `client_v1.pem` and trust `ca_v1.pem`.
    *   Call `SayHello`.
    *   Call `RotateCert` to make the server switch to `server_v3.pem` (still using `ca_v1.pem`). Client reconnects.
    *   Call `SayHello`.
    *   Call `RotateCert` again. Server switches to `server_v2.pem` (using `ca_v2.pem`).
    *   Client calls `GetNewCACert`, updates its trust to `ca_v2.pem`, and reconnects.
    *   Call `SayHello`.
    *   Call `RotateCert` again. Server switches back to `server_v1.pem` (using `ca_v1.pem`).
    *   Client calls `GetNewCACert`, updates its trust to `ca_v1.pem`, and reconnects.
    *   Call `SayHello`.

## How Rotation is Simulated

*   **Server:** The `RotatingCertServer` class in `server.py` manages the current certificate paths. The `RotateCert` RPC cycles through predefined certificate versions (`server_v1`, `server_v3_ca_v1`, `server_v2_ca_v2`). When rotating, it updates its configuration and then stops and restarts its underlying `grpc.aio.Server` instance. This is a simplified approach; a production server might use more advanced techniques for zero-downtime rotation (e.g., socket options like `SO_REUSEPORT`, multiple server instances, or dynamic updates if the gRPC library supports them fully).
*   **Client:** The `client.py` script maintains `CURRENT_CA_VERSION`. After a rotation that involves a CA change, it calls `GetNewCACert`, saves the new CA PEM locally (for inspection, named `ca_v2_from_server.pem`), and then updates `CURRENT_CA_VERSION`. It then re-creates the `grpc.aio.Channel` with credentials trusting the new CA.

## Limitations and Further Exploration

*   **Downtime during Rotation**: The current server simulation involves stopping and restarting the gRPC server, which means active connections will be dropped. True zero-downtime rotation is more complex.
*   **Client Certificate Rotation**: This example focuses on server certificate rotation and client CA trust updates. A full scenario might also involve client certificates expiring and needing rotation, which would require the client to obtain a new certificate (possibly from a new CA) and the server to be configured to trust clients signed by that new CA.
*   **Error Handling**: The example includes basic error handling, but production systems would need more comprehensive resilience strategies.
*   **Discovery of New CA**: The client currently relies on an RPC call (`GetNewCACert`) to the *same server* to get the new CA. If the server has already fully switched to a new CA that the client doesn't trust, this call itself might fail due to SSL handshake issues. Alternative discovery mechanisms (e.g., a separate discovery service, out-of-band distribution) are common.
*   **Automatic Rotation**: Rotation is triggered manually via an RPC. Automatic rotation based on impending expiry would require persistent state, timers, and more robust monitoring.
*   **Graceful Shutdown of Plugin**: The `PLUGIN_SHUTDOWN_FILE_PATH` mechanism from `pyvider-rpcplugin` is not explicitly used here as the server is run directly, but a plugin implementing such a server could use it for controlled shutdown signals.

This example provides a foundational look at the mechanics of certificate rotation in an mTLS gRPC setup.
