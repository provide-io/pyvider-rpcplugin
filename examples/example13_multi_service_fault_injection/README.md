# Example 13: Multi-Service Plugin with Inter-dependencies, Broker, and Fault Injection

This example showcases a `pyvider-rpcplugin` plugin that hosts multiple gRPC services (`ServiceA`, `ServiceB`, `ServiceC`) with dependencies on each other. It demonstrates:

1.  **Internal Service Calls**: `ServiceA` calls `ServiceB`, and `ServiceB` calls `ServiceC`, all within the same plugin instance.
2.  **GRPCBroker for External Calls**: `ServiceA` uses the `GRPCBroker` to call an `ExternalMockService`, which is implemented and served by the `client_app.py` (acting as a separate system component).
3.  **Fault Injection**: A simple fault injection mechanism (`fault_injector.py`) is used to simulate delays or errors at various points in the call chain (e.g., between A and B, B and C, or before calling the external service).
4.  **Retry Logic**: Basic retry mechanisms are implemented for some internal and external calls.
5.  **Plugin and Client mTLS**: The plugin itself can be configured for mTLS, and `client_app.py` connects to it using mTLS. The broker communication also respects this security.
6.  **Complex Asynchronous Workflows**: Demonstrates managing asynchronous calls across multiple services.

## Architecture

```
+---------------------+      gRPC (mTLS)      +---------------------------------------------+
|   ClientApp         |<--------------------->| Plugin (plugin_main.py)                     |
| (client_app.py)     |      (ServiceA)       | +-----------------------------------------+ |
|                     |                       | | ServiceAImpl                            | |
| - Calls ServiceA    |                       | | - Calls ServiceB (internal)             | |
| - Serves            |                       | | - Calls ExternalMockService (via Broker)| |
|   ExternalMockService|                       | +-----------------------------------------+ |
+---------------------+                       | | ServiceBImpl                            | |
          ^                                   | | - Calls ServiceC (internal)             | |
          |                                   | +-----------------------------------------+ |
          | GRPCBroker                        | | ServiceCImpl                            | |
          | (ExternalMockService)             | +-----------------------------------------+ |
          v                                   |                                             |
+---------------------+                       | GRPCBroker Service (part of PluginServer)   |
| Plugin's Broker   |<--------------------->| - Relays calls to/from ClientApp's Broker |
| Client Component    |      (brokered)       +---------------------------------------------+
| (in ServiceAImpl)   |
+---------------------+
```

## Files

*   `service_a.proto`, `service_b.proto`, `service_c.proto`: Define the internal gRPC services.
*   `external_mock_service.proto`: Defines the external service called via the broker.
*   `services_impl.py`: Contains Python implementations for `ServiceA`, `ServiceB`, and `ServiceC` servicers.
*   `fault_injector.py`: Simple module to introduce delays or errors.
*   `plugin_main.py`: Entry point for the plugin. Initializes `PluginServer`, registers all services, sets up an internal channel for service-to-service calls, and configures example faults.
*   `client_app.py`: Simulates an external application. It acts as a client to `ServiceA` and also *serves* `ExternalMockService` so the plugin can call it back via the broker.
*   `README.md`: This file.
*   `__init__.py`: Makes the directory a Python package.
*   `.plugin_certs/`: Directory (auto-generated by `plugin_main.py`) containing self-signed certificates for the plugin's own mTLS endpoint.
*   `.client_app_certs/`: Directory (partially auto-generated by `client_app.py`) for certificates client_app uses. `client_app.pem` and `client_app.key` need to be manually created or signed by `.plugin_certs/plugin_ca.pem` for mTLS to plugin.
*   `*_pb2.py`, `*_pb2_grpc.py`: Generated Python code from `.proto` files.

## Prerequisites

*   Python 3.8+
*   `grpcio`, `grpcio-tools`
*   `pyvider-rpcplugin`

Install dependencies (preferably in a virtual environment):
```bash
pip install grpcio grpcio-tools pyvider-rpcplugin
```

## Running the Example

1.  **Generate Protocol Buffers Code**:
    Navigate to the `examples/example13_multi_service_fault_injection` directory and run:
    ```bash
    python -m grpc_tools.protoc -I. --python_out=. --grpc_python_out=. *.proto
    ```
    This generates Python files for all defined services.

2.  **Start the Plugin Server**:
    In a terminal, run:
    ```bash
    python plugin_main.py
    ```
    This will:
    *   Generate self-signed certificates for the plugin's mTLS endpoint (if not already present in `.plugin_certs/`).
    *   Start the `PluginServer` on `localhost:50052` (default).
    *   Register `ServiceA`, `ServiceB`, `ServiceC`.
    *   Enable the `GRPCBroker`.
    *   Configure some default fault injection scenarios.

3.  **Prepare ClientApp Certificates (Important for mTLS)**:
    The `plugin_main.py` sets up the plugin in mTLS mode by default. This means `client_app.py` needs a valid client certificate and private key signed by the CA that `plugin_main.py` trusts for its clients.
    *   `plugin_main.py` generates its own CA (`.plugin_certs/plugin_ca.pem`) and its server certificate (`.plugin_certs/plugin_server.pem`) signed by this CA.
    *   You need to:
        1.  Take `.plugin_certs/plugin_ca.pem` (and its key, `plugin_ca.key`, which is also generated for simplicity in this example but would normally be secure)
        2.  Generate a client certificate/key pair for `client_app.py`.
        3.  Sign this client certificate using `.plugin_certs/plugin_ca.pem` and `.plugin_certs/plugin_ca.key`.
        4.  Place the generated client certificate as `.client_app_certs/client_app.pem`.
        5.  Place the generated client private key as `.client_app_certs/client_app.key`.
    *   `client_app.py` will also need to trust the plugin's server, so it uses `.plugin_certs/plugin_ca.pem` as its `PLUGIN_SERVER_CA_CERT_PATH`.
    *   If these certs are not correctly set up, the mTLS connection from `client_app.py` to the plugin will fail. `client_app.py` creates placeholder files if they are missing, which will cause mTLS to fail.

4.  **Run the Client Application**:
    In another terminal, run:
    ```bash
    python client_app.py
    ```
    This application will:
    *   Attempt to connect to the plugin's `ServiceA` using mTLS (certs from step 3 are crucial).
    *   Start serving `ExternalMockService` via the `GRPCBroker`, making it available for the plugin to call.
    *   Send various requests to `ServiceA` to trigger different call paths (internal calls, broker calls).
    *   Log responses and any errors encountered due to fault injection or other issues.

## Fault Injection Configuration

*   Faults are defined in `fault_injector.py`.
*   `plugin_main.py` (via `services_impl.configure_example_faults()`) sets up some initial fault probabilities and types (e.g., delays, RPC errors).
*   You can modify these configurations directly in `services_impl.py` or potentially expose an RPC to change them dynamically for more advanced testing. Fault points include:
    *   `ServiceA_Processing`: Fault within ServiceA itself.
    *   `ServiceA_to_ServiceB`: Fault during the call from A to B.
    *   `ServiceB_Processing`: Fault within ServiceB itself.
    *   `ServiceB_to_ServiceC`: Fault during the call from B to C.
    *   `ServiceC_Processing`: Fault within ServiceC itself.
    *   `ServiceA_to_ExternalBroker`: Fault before ServiceA attempts to use the broker.
    *   `ExternalService_Processing`: Fault within the `ExternalMockService` served by `client_app.py`.

## Key Features Demonstrated by `pyvider-rpcplugin`

*   **`PluginServer`**: Hosts multiple gRPC services.
*   **`RpcPluginConfig`**: Centralized configuration for paths, security, logging, etc.
*   **`GRPCBroker`**: Enables the plugin (`ServiceA`) to make outbound gRPC calls to services hosted outside the plugin (i.e., `ExternalMockService` in `client_app.py`). `client_app.py` also uses `GRPCBroker` client-side functionality to serve its `ExternalMockService` through the broker system.
*   **mTLS Security**: Both for the plugin's main endpoint and potentially for brokered services.
*   **Handshake Protocol**: Ensures secure and versioned startup. (Magic cookie is used here).
*   **Shutdown File**: `PLUGIN_SHUTDOWN_FILE_PATH` is configured, allowing graceful shutdown by creating the specified file.

This example provides a comprehensive testbed for developing and debugging complex plugin interactions.
